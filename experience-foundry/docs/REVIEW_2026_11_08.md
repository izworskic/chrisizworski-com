# Foundry 0.3: executable improvement cycle

## Problem

Foundry 0.2 produced useful planning packets and safe previews, but an agent could call a modest source-link addition a completed improvement without demonstrating a changed visitor outcome. Rocket PR #1565 exposed this gap: its new contextual guide link omitted the selected mission ID while hiding the older ID-preserving link.

## Implemented system change

`improve` captures committed source and gives the agent an implementation assignment. `assess` requires a diagnosis, three investigated opportunities, two viable designs for the selected opportunity, observable before/after scenarios and distinguishable measurement. `prove` actually runs the same local adapter against baseline and current source. It records observations, rejects regressions and unmet outcomes, and cannot turn an adapter crash into a favorable baseline failure. `assess --proof` rejects drift in the implementation, assignment or adapter.

This is not an autonomous research service. The agent still makes and reviews the product decisions. Structural checks do not prove the credibility of prose, originality, source truth or real visitor benefit. There is no new public UI or compulsory template.

## Real diagnostic replay

On November 8, the included Rocket example captured commit `9221c3e638e2e30d564c6d3e3479bad0ed90dde0` and replayed against the same current Rocket implementation. The selected Florida UUID was `22222222-2222-4222-8222-222222222222`. The contextual link resolved to `/national-tools/space-coast-launch/` without `launchId` in both passes. The unavailable-source NASA fallback remained usable in both.

Foundry returned **NOT_DEMONSTRATED**: selected-mission handoff UNMET; unavailable-source fallback PRESERVED; zero changed product files. Completing the research record and preserving a fallback could not turn this into a successful improvement claim. This is a bounded model replay; it does not test a browser destination, return journey, live launch state or all six regions. No Rocket product code was changed in this system task.

The synthetic regression suite separately demonstrates a real code correction becoming GAIN while preserving an existing capability, and rejects a candidate that fixes selection while inventing an empty-state destination. Synthetic fixtures test Foundry mechanics, not Rocket improvements.

## Acceptance boundaries

- Meaningful tests cover incomplete assignments, unchanged implementations, genuine gains, regressions, adapter errors, omitted/duplicate results, stale code/adapter/assignment proof, edited baseline content, invalid evidence references and path/symlink boundaries.
- Existing recipe browser acceptance and full owner CI remain required. This change does not alter either recipe's visitor-facing rendering or styles.
- No production deployment, traffic, CTR or revenue benefit is asserted by this record.
- The next product action is to use the cycle on the active Rocket improvement work, extending the proof to the loaded regional mission and return journey. Do not duplicate that product work in a second branch.

## Local validation

The full owning-repository gate passed all 60 steps. The final focused Foundry suite passed 28 tests, including the new-module baseline case. Existing recipe browser acceptance passed all 50 cases at 360, 390, 768 and 1440 pixels; representative mobile passage and desktop journal screenshots were inspected. These results establish local checks only; hosted PR checks, merge and any downstream product release remain separate.
