## Proposed visual contract
A. Platform primitives: inventory existing styles before choosing any shared values. Define roles for body, editorial heading, tool heading, primary reading, supporting data, label and caption; spacing/gaps, surface, text, accent, focus, border, radius and elevation; action hierarchy and accessible semantic states. Start with existing approved values where compatible; use semantic aliases, not a second arbitrary palette. Keep default body type readable (16 CSS px starting point, not a hard ban on smaller metadata); WCAG AA and existing accessibility requirements always govern. For tabular values, align units and precision. Do not select a universal font/palette until actual screenshots and contrast are reviewed.

B. Component contracts: shared behavior and semantic roles for breadcrumbs/navigation, tool identity, action/link, input, selected state, data timestamp/source, loading/error/unknown, map controls, popup, legend, map/list selection and photo credit. Reuse an existing tested implementation where suitable. Document default, selected, focus, disabled, loading, empty, stale, error and no-JS states as applicable. A missing state must not look successful. Document a justified exception when a task requires different behavior. No universal card shell. Related products should use consistent vocabulary, icon meaning and map interaction, e.g. vessel silhouette by class and one popup for a single selection. Shared status colors must not reverse meaning across products; always add text or shape, never color alone.

C. Product families (examples, not templates):
- Live intelligence (freighters, aurora, ice, weather): answer or evidence, observation time, relevant map/trend, clear uncertainty. Operational density is legitimate.
- Geographic exploration (waterfalls, beaches, parks): recognizable geography and credited exact-place photography, selected detail and access, map/list alternatives.
- Planning (garden, holiday travel, scenic journeys): meaningful input, actionable recommendation or timeline, tradeoffs and saved state if supported.
- Interpretive experiences (locks, bridges, natural phenomena): annotated diagram, sequence, grounded explanatory copy and optional interaction.
Keep composition, typography emphasis, photography, subject accents and meaningful interactions task-specific. Never use family names as visible filler. No same-page clone test is waived for sibling tools.

## Anti-slop review: find, explain, subtract
For each major visible element identify its job: answer, action, comparison, evidence, orientation or genuine interpretation. Remove decoration or duplicate prose when it serves none. Preserve required factual indexed prose and source links, moving secondary information only when permitted.
- Hero without a useful first-screen answer, arbitrary marketing kicker, title repeated in multiple sections, unrelated image, empty visual weight: replace with purposeful hierarchy.
- Every section boxed, equal emphasis on unrelated data, nested card stacks, decorative gradient/glow, badge wall, indiscriminate pills, gratuitous icons or animation: group by meaning and use typography/spacing first. A gradient or rounded surface is not automatically wrong; justify its communicative purpose.
- Weak contrast, washed-out labels, buried units, oversized metadata or microscopic controls: ensure answer and actions dominate, accessible contrast and targets.
- Internal implementation jargon, invented precision, generic promotional or inspirational filler: use plain-voice and existing interpretive guidance; retain sources and uncertainty.
- Inconsistent sibling map symbols/status meanings, duplicate selection panels, map without usable touch or keyboard behavior: use shared tested contracts and verify state.
- Unnecessary chart, map or interactive effect with no changed visitor decision: remove or replace with the appropriate representation.
- Stale/unknown disguised as live, synthetic place photo as evidence, ads overlapping answer/map/hero: existing hard gates, no workarounds or changes to ads settings.
Do not infer machine authorship from a style trait; judge observed usefulness, execution and continuity. Do not count cards, ban all gradients or assign a fake AI-slop probability. A good page can be expressive, dense or quiet as its job requires.

## Proposed evidence and acceptance (reuse existing scorecard, no competing numerical grade)
For substantial work add one compact design acceptance record to the existing brief/release review:
1. Primary visitor question and first-screen answer/action, inspected at 390 and 1280 CSS px. On exceptional tasks where the answer needs input, show the input and explain how the result is reached.
2. Two nearest tools: screenshot comparison with what is shared (navigation/action/status/type/interaction) and at least two meaningful task-led distinctions required by existing OS. For related tools, record actual component reuse or a justified exception.
3. Identify canonical component/style source, semantic roles, and any new variant plus justification. Record which visible element was removed/simplified or why nothing should be removed. Identify unresolved inconsistencies explicitly.
4. Inspect actual before/after screenshots at stable fixture state and relevant selected, loading, stale, error, keyboard focus states; mobile and desktop. Run existing full responsive matrix and relevant browser, contrast and interaction checks. Mask only nondeterministic content in image comparisons (never mask critical answer, controls or data labels). Screenshot diffs detect change, not quality. No blanket snapshot update to silence a regression.
5. Record PASS / FAIL / NOT VERIFIED for hierarchy, family continuity, functional distinctiveness, visual craft and failure states. Reviewer must cite observable evidence, not just adjectives; existing weighted scorecard remains authoritative. Proposed acceptance veto for unjustified inconsistency that breaks meaning or interaction, unreviewed cloned composition, or critical hierarchy failure. Unreviewed design evidence is NOT VERIFIED, not pass. No visual score from source alone. Fix user-critical problems before cosmetic debt.
6. Preserve all SEO, canonical/Person, ads, data, performance, source rights, cost and owning-repo gates. No new paid services, infrastructure or broad migration. Browser QA and actual visitor outcomes remain separate from CI.
