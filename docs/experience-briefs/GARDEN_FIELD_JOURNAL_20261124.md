## Decision and design
Visitor asks what actually happened with this crop, not merely what the calendar predicted. Three opportunities: record crop milestones (high utility, low cost); compare reported daily and paired night temperatures to existing scientific engines (useful, constrained by complete data); automatic field calibration (blocked by lack of independent outcomes). First two implemented, third withheld. Compared a global chronological diary (low input overhead but mixes bed/variety cohorts) with per-planting dated field notebook (selected crop, bed, planting date, event list and model comparison). Choose per-planting; successive sowings are separate IDs. Unlike the existing planting planner's calendar of suggested dates and growing-season notebook's historical model ranges, the journal's primary output is the visitor's own recorded events, including first flowering, fruit set and harvest; reference ranges are secondary and explicitly not observed harvests. Existing links and page hierarchy preserved. No new route, image, hero, ad slot or generic dashboard. Source evidence is inherited from GARDEN_WEATHER_EVIDENCE_V1.md and GARDEN_INTELLIGENCE_ENGINES_V1.md; no new provider or proprietary content.

## Technology and data contract
Existing semantic HTML, scoped CSS, browser JS; versioned local storage (fvfFieldJournalV1), no remote writes, database, private-coordinate collection, dependencies, build steps or production functions. Existing Node weather bridge is not changed. Python useful for offline independent validation, not needed for the local diary; Java and Rust/WASM add no measured benefit. JSON backup/restore validates all IDs, links, dates, types and temperature coverage before replacing an empty journal. Existing records cannot be overwritten by import; malformed stored data is preserved and the session is explicitly unsaved. Removal of a planting requires confirmation, removes its observations; individual entries removable. Up to 100 plantings, 4000 observations, notes 1000 characters. No account or cloud sync. The crop model link is set only through explicit growing-season handoff, must match biofix, and is cleared on crop text changes. Actual planting date must not be in the future. Model comparison requires matching observed endpoint, location, planting month/day and all five historic crossings. Packet comparison assumes the packet dates refer to the recorded starting stage. No inference of actual harvest from GDD.

Daily-air entries must be a completed local day with visitor-asserted shielded sensor coverage. Only consecutive days from planting are used; no gap fill; historic cohorts evaluated within 365 days. Paired-night entries require matched previous 18:00 to 09:00 local windows, comparable air sensors, matching reference name and regime; at least five unique past nights within 90 days for the existing microclimate sensitivity scenario. Reference low manually entered, not a measured garden forecast. No probability or safety guarantee. All observations are self-reported; no independent validation or automatic learning claim.

## Return contract and failure states
Return after actual flowering, harvesting or a measured night; saved per-planting history and packet comparison improve as user records evidence. No alerts, no push, no invented engagement baseline. Return share and GSC outcomes NOT MEASURED. Switching plantings retains records and clears stale comparison; unsupported variety still records notes and packet dates; incomplete data never fabricated; no-JS fallback retains guides. Export file is private to user; no cross-device sync unless user restores backup. Browser storage unavailable: session-only warning. Historical archive failure: actual notes remain.
