# Gatlinburg Winter competitive benchmark — September 24, 2026

This is an internal product benchmark based on publicly visible pages found across current Gatlinburg winter, Christmas, December and January search intent. It is not an independent usability study and the scores are not claims about measured traffic, conversion or user satisfaction.

The product goal is narrower than a tourism portal: answer **what should I do on my actual date, with my available time and current constraints, and what do I need to recheck before committing?**

## Features required to clear the benchmark

### First screen
- no giant promotional hero
- one qualitative decision read
- only the few conditions that can change the answer
- exact seasonal anchors must come from official sources

### Plan
- one complete schedule before alternatives
- JEV remains closed-set and can only choose already-feasible schedules
- retain cost, walking, exposure, movement and verification context

### Need-to-know stop layer
Selected stops should support:
- scheduled time and dwell
- cost class
- plan-ahead / ticket signal
- walking burden
- weather exposure
- why it belongs at that point in the day
- execution note
- official source link

### Operations
- distinguish downtown parking from park parking
- NPS parking-tag requirement when relevant
- winter trolley cutoff awareness
- fixed-event traffic / circulation recheck
- mountain weather kept separate from downtown weather
- Ober operating status never inferred from downtown snowfall

### Date intelligence
- selected date remains a decision variable
- nearby dates rerun the planner instead of copying selected-date weather
- fixed events and sunset changes are explicit

### Search-depth layer without article bloat
- November / December / January / February framing available as structured product data
- exact Winter Magic window
- exact 2026 Christmas parade anchor
- concise winter elevation / weather context

## Severe loss conditions

Do not ship if any of these regress:
- closed attraction recommended as open
- future weather represented as live outside a trustworthy forecast window
- selected-day weather reused for nearby-date comparison
- downtown snow used as evidence Ober snow operations are running
- parking availability invented
- trolley route certainty invented from general hours
- NPS road status weakened or hidden when a park segment is selected
- the actual plan is buried below generic tourism copy

## Result of the benchmark finish pass

### Shipping in the current visible planner
- preserved the proven v3.5 planner runtime and its complete-schedule selection model
- preserved Decision Clock, Date Intelligence, hard gates, source hierarchy, degraded states and selected-plan-only map
- added an additive visual polish layer to the existing navigation, official checks, personalization controls, itinerary, evidence cards, alternatives, commit section, map and supporting data
- kept the first screen decision-first instead of replacing it with a promotional tourism hero
- kept the runtime direct and race-free; the benchmark work does not replace the canonical planner script

### Added as backward-compatible structured API data
These are additive fields for future UI surfacing and do not replace the v3.5 response contract:
- `planBrief`
- `stopFacts`
- `seasonFacts`
- `lookNow`
- `commitChecks`
- `monthGuide`
- `benchmarkVersion`

The existing `version` and `commitChecklist` fields remain owned by v3.5 so existing frontend behavior and tests are not silently changed.

### Deliberately not claimed as visible yet
The finish pass does **not** claim that the API-ready plan brief, month guide, live-check cards or expanded stop-fact blocks are already rendered as separate new page sections. They are staged as structured data until they can be surfaced without weakening the planner's existing tested runtime.

The benchmark pass is considered shippable only when repository verification passes and the production deployment/runtime is independently checked.
