# Garden intelligence engines v1

Engine-only pilot; not connected to public UI. No new routes, dependencies, cron, API calls, private storage, ads, canonical or SEO changes. Existing garden planning and seasonal heat endpoints are unchanged. Browser globals GardenMicroclimate and GardenHarvest and CommonJS exports use the same source.

## Architecture
Keep lightweight deterministic JS for browser and Node; offline Python is appropriate for future independent paired-station and crop outcome backtesting, not required for these computations. Request-time Python or new network services add cost and latency without evidence of improvement. Prototype gates: descriptive/scenario only; prediction release blocked on local independent validation, provider rights and data adapter review. No accuracy or search-uplift claim.

## Microclimate
GardenMicroclimate.assess accepts siteId, referenceId, asOf and referenceDate (local ISO calendar dates), referenceLowF, regime (clear-calm, cloudy-windy, other), optional thresholdF (default 32), site flags and pairs. Each pair requires date, matching identifiers/regime, sameNightWindow and comparableShieldedAirHeight true, gardenLowF and referenceLowF. All temperatures Fahrenheit. Only past nights within 90 days; reference horizon 0–7 days; conflicting dates omitted. Five unique nights is a display minimum, not statistical calibration. Offsets are garden minus reference; median plus observed extremes applied to supplied low is an illustrative sensitivity scenario, not a forecast interval or guarantee. Site factors never invent offsets. No source-specific numeric adjustment for lakes, covers, shade, soil or wind. Callers must establish timestamp alignment, sensor height and shielding, weather classification, and source provenance; this engine cannot verify caller assertions. Never use this output to declare plants safe. Read https://msu-prod.dotcmscloud.com/news/monitoring_for_the_risk_of_frost_and_freezing_temperatures for cold air drainage and radiation freeze context.

## Harvest
GardenHarvest.evaluate accepts modelId, exact biofix, plantingDate, asOf, siteId, optional packetDays and daily weather array (date, siteId, source, kind, minF, maxF, issuedDate for forecast). Local calendar dates; Fahrenheit. Observed days before asOf; same-day-issued forecast days from asOf through +7 only. Daily weather records must represent full local days. Start on supplied planting/biofix date including that day's daily heat, a day-resolution convention; no hourly adjustment. Do not use season-wide USA-NPN base-50 cumulative heat for cultivar models. The adapter at api/garden-seasonal-heat.js remains seasonal context only.
The 16 cultivar/stage/endpoint entries use numeric parameters from Oregon State Extension EM 9305 tables 1, 2, 3, 5, 6: https://extension.oregonstate.edu/catalog/em-9305-vegetable-degree-day-models-introduction-farmers-gardeners . Single sine horizontal cutoff is integrated analytically as area above lower threshold minus area above upper threshold. Source study primarily western Oregon 2013–15, not independent Michigan validation; no reuse of copyrighted prose, images or code. Calendar baseline is packet days from caller-confirmed biofix or reported trial mean when endpoint matches. Unknown varieties are not mapped to another cultivar. No invented forecast beyond input coverage, no gap filling or forecast probabilities; threshold crossing is calculated scenario, not observed maturity. For operational integration, obtain source permission and timestamped NOAA/MSU weather records or garden sensor records; separate actual from forecast, archive forecast vintages.
