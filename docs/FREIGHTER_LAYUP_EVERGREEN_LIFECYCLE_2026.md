# Evergreen Great Lakes winter layup lifecycle (November 2026)

## Visitor contract

**The current shipping winter is always the shipping winter containing the visitor's date, using the November 1 rollover in America/Detroit.** A year can contain a current season with no documented winter berths. No source-backed report is **not** proof that no freighters are in the harbor.

The selector always leads with the current winter, not last year's more populated archive. All earlier frozen seasons remain accessible, including winters with no collected reports. The curated historical sections are server-readable HTML generated by offline Python, not client-only pages. The page's canonical and established map, photography, AIS caveats, source classifications, ad exclusions and biographies are retained.

## Lifecycle

1. **During winter:** existing Node scanner observes configured publishers and accepts only dated, permitted evidence. The current `public/assets/freighter-layup-live-season.json` grows with arrivals, moves, maintenance and departures. An empty ledger remains truthful. Python does not manufacture or confirm arrivals.
2. **November 1 (America/Detroit):** existing Node `seasonForDate()` and `rollover()` close the previous winter and write a fresh ledger. Even empty winters enter `previousSeasons`; missed scan years become explicit empty archives rather than vanishing.
3. **Same scheduled job:** `scripts/freighter-layup/evergreen.py` validates every previous winter's source/event fields, reconciles it against the curated historical registry without overwriting curated records, freezes the prior year's ships into `historical_snapshot` and creates the empty current-season slot. No AIS location/velocity is processed. The completed year's event timeline retains arrival, departure, source and confidence. Registry snapshots persist independently even after the live ledger rotates through its rolling 12-winter buffer.
4. **Static regeneration:** Python regenerates `freighter-layup-history.json` and the crawlable `WINTER_FLEET_HISTORY` HTML with a dynamic historical winter count, including an explicit "no source-backed reports were collected" message for zero-report years. The static season dropdown and live desk label update automatically. If the HTML changed, the page's `dateModified` and sole `sitemap-winter.xml` lastmod update together. Static biography generation and Node registry validation run before publication.
5. **Browser fallback:** `freighter-layup.js` determines the winter in Detroit time even if a scan is late or its JSON cannot load; it creates only a **provisional empty current-season view**. It rejects a stale prior-winter ledger as live and never makes last winter's berths current. Users can navigate any source-backed historical winter; old hard-coded archive and harbor defaults are gone.

## Engineering choice

- **JS-only:** already had a winter calculator, but hard-coded frontend selection and a fixed registry blocked 2027–28 and beyond.
- **Python companion:** selected. The scheduled and offline reconciler performs source validation, static archive generation, HTML/JSON consistency and year rollover. Existing Node remains source authority; JavaScript owns the interactive map. No new runtime servers, Redis, Supabase, external provider requests, new canonical URLs or paid dependencies.
- **Server-side Python service:** rejected. It would add uptime/cost and dynamic rendering uncertainty for a once-a-year transition.

## Consistency/fail-closed rules

- Never clone a prior year's ship records, photo locations, pins, berth confidence, or AIS into a new winter.
- Preserve source URL, original source class, original dated event, confidence and vessel key; unknown identity is not quietly matched to known names.
- A reported source stays reported. A community or journalistic source cannot be rewritten as confirmed.
- A departure remains part of the historical timeline. "Historic winter stay" does not assert continued present occupancy.
- Validate before writing; reject duplicated events, impossible dates, invalid harbors, unknown source classes, stale/future ledgers, mismatched year pairs, backward movement and unexpected changes to prior curated winters.
- Preserve empty historical years with uncertainty language; no fabricated fleet census totals.
- Keep annual registry snapshots indefinitely. The transient live ledger retains up to 12 previous winters, with prior frozen history already in the durable registry.
- If GitHub Actions fails, it does not publish a bad or partially validated archival change; the browser still labels the actual current winter as provisional.

## Test matrix

Run `python3 -m unittest discover -s scripts/freighter-layup -p 'test_*.py'`, targeted Node tests including `tests/freighter-layup-evergreen.test.js`, the full `npm run verify:all`, and the real-browser release test.

Fixture cases include Detroit midnight 2027, 2028, 2029, 2034; repeat-run idempotence; skipped years; empty winters; two different source confidence classes; documented arrivals and departures; impossible event dates; missing sources/harbors; orphan departures; duplicate evidence; missing sitemap; and delayed or absent live JSON. The tests explicitly verify the current winter is selected by default even with no arrival.

## Operational note

The existing source watcher runs four times daily Nov–Apr, with a dedicated Nov 1 UTC publication pass after Detroit midnight. It commits only when the ledger, archive, page, biographies or sitemap actually change. No annual manual copy of the tool or dropdown is required. GitHub Actions can be delayed or disabled; the browser fallback is truthful, and the next successful scan reconciles missed winters.

## Scope boundary

This solves the **evergreen season lifecycle**. It does not mean the feed scanner now discovers every layup; that separate evidence-recall research still requires source coverage and prospective review validation. It does not prove any ship is currently laid up, and no ranking or CTR uplift is claimed without comparable postrelease data.
